> 애드센스 재도전은 별도 저장소(자체 도메인 사이트)에서 진행한다. 경과는 [`ADSENSE_PROGRESS.md`](../ADSENSE_PROGRESS.md) 최상단.

> 디자인 스킬(hallmark·web-design-guidelines)과 카드·썸네일 비교 결과는 [`DESIGN_SKILLS.md`](../DESIGN_SKILLS.md). 웹 UI 작업 때만 읽는다.
> 15편부터는 벤치마크 템플릿 시험 중이다(명세 [`donsalimpyo-post-harness.md`](../donsalimpyo-post-harness.md), 적용 방식·판정 기준은 `NAVER_GUIDE.md` 「벤치마크 템플릿 시험」). 원고를 쓰기 전에 그 절을 읽는다.

## 저장소 운영 — 한 저장소에 프로젝트가 둘이다

| | 블로그 | SNS 하네스 |
|---|---|---|
| 경로 | 루트 전체 (아래 둘 제외) | `sns_harness/`, `.github/` |
| 작업 위치 | 이 폴더, `main` | 별도 작업폴더(`블로그/.worktrees/…`), `codex/*` 브랜치 |
| 올리는 방식 | 직접 커밋 후 푸시 | PR |

2026-10-05에 블로그 커밋 푸시가 거부됐다. 이 폴더의 `main`을 받아온 적이 없어 원격보다 34커밋 뒤였고,
SNS 쪽 옛 작업물 34개 파일이 미커밋으로 남아 `git pull`도 막혀 있었다.

**블로그 세션(이 폴더)의 규칙**

- 순서는 `git pull` → 작업 → `git add <파일 지정>` → 커밋 → `git push`. `git add -A`·`git add .`는 쓰지 않는다.
- 커밋 전에 `git diff --stat`로 바뀐 줄 수가 고친 범위와 맞는지 본다. 2026-10-14에 파이썬 패치 스크립트가
  텍스트 모드로 써서 `check_naver.py` 전체를 CRLF로 바꿨다(639줄 전부 변경). 스크립트로 파일을 고칠 때는 `newline=''`로 읽고 쓴다.
- `sns_harness/`·`.github/`는 **읽기만 한다.** 수정·커밋하지 않고, 문제를 발견하면 사용자에게 전달한다.
- 이 폴더에서 `sns_harness/`·`.github/`가 미커밋 변경으로 보이면 이상 신호다. 커밋하지 말고 보고한다.
- 푸시가 거부되면 강제 푸시하지 않는다. `git pull`(이 저장소는 `pull.rebase=true`) 후 다시 푸시한다.
- `push-work/`는 상위 `Claude_code` 저장소의 작업폴더다. 이 저장소에서는 무시한다(`.gitignore`).

## 커밋 규칙 — 재발 방지를 같은 커밋에 넣는다

**사용자가 "커밋하자"고 하면 코드만 담지 않는다.** 그 세션에서 실제로 발생한 문제에 대해
구조적 재발 방지까지 같은 커밋에 포함한다. 사용자가 따로 요청하지 않아도 한다.

### 커밋 전 점검 (매번)

1. **이번 세션에서 무엇이 어긋났는지 적는다** — 버그, 잘못된 보고, 조용히 깨져 있던 검증,
   틀린 안내, 사용자가 두 번 지적한 것. "고쳤으니 됐다"로 넘기지 않는다.
2. 각 항목에 대해 **"같은 일이 또 생기면 무엇이 먼저 알려주나?"**를 답한다.
   답이 "아무것도 없다"면 그 자리에 장치를 만든다.
3. 장치를 만들고 **실행해서 통과를 확인한 뒤** 커밋한다.

### 방지 수단의 우선순위

높은 것부터 시도한다. **문서만 추가하는 것은 최후 수단이다** — 문서는 안 읽히면 아무것도 막지 못한다.

| 순위 | 수단 | 예 |
|---|---|---|
| 1 | 코드가 스스로 깨지게 | `--selftest`에 실제 표기법을 합성 입력으로 고정, 함수 진입부 `assert` |
| 2 | 검사 스크립트에 항목 추가 | `verify_naver.py`의 카테고리 일치·발행 간격·태그 중복 |
| 3 | 실패 시 종료 코드 | 게이트가 통과처럼 보이지 않게 `sys.exit(1)` |
| 4 | 문서 규칙 | 위 셋으로 표현할 수 없는 판단·운영 규칙만 |

### 커밋 메시지

**무엇을 고쳤는지가 아니라 무엇이 왜 깨졌는지를 쓴다.** 나중에 같은 패턴을 알아보기 위해서다.
숫자가 틀렸으면 틀린 값과 맞는 값을 같이 적는다(예: 1,505자를 1,728자로 보고했다).

### 같은 패턴이 두 번 이상이면

`파이프라인 기술 노트`의 재발 이력 표에 행을 추가한다. 세 번째부터는 개별 수정이 아니라
**패턴 자체를 막는 장치**를 만든다(셀프테스트 고정이 그 예다).

### 범위 가드

- **이번 세션에서 실제로 발생한 문제만** 다룬다. 있을 법한 문제를 가정해 미리 만들지 않는다.
- 재발 방지가 커져서 별도 작업이 되면, 커밋을 나누고 사용자에게 무엇을 분리했는지 말한다.
- 사용자가 지적하지 않은 기존 코드를 이 명목으로 리팩터링하지 않는다.

`gap`이 경고한다. 사용자가 직접 주제를 주면 이 단계는 건너뛴다.

## 블로그 매니저 — 판정은 코드가, 전달은 그대로

"블로그 매니저 브리핑", "블로그 상황", "블로그 오늘 뭐 해야 돼"라고 하면 `blog-manager` 에이전트를 부른다.
SNS 운영 매니저(`python -m sns_harness operations …`, 매일 07:45 KST에 Notion으로 브리핑)와는 별개다 —
그쪽은 Threads 컨셉을, 이쪽은 네이버 블로그 컨셉을 판정한다. 그냥 "매니저 브리핑"이라고만 하면 어느 쪽인지 되묻는다.
에이전트는 `python -X utf8 manager.py`를 돌려 발행 현황·방문자·데이터 신선도를 모으고,
판정과 오늘 할 일(최대 3개)을 보고한다.

**판정 기준은 `manager.py` 상단 상수에만 있다**(2026-10-05 확정, 네이버 블로그 대상).

| 점검 시점 (먼저 오는 쪽) | 7일 평균 일 방문 | 미달 시 |
|---|---|---|
| 10편 또는 첫 발행 4주 | 15명 | 경고 |
| 20편 또는 첫 발행 8주 | 50명 | 전환권고 |

방문자 수치가 7일 넘게 비면 `판정보류`다. 수치는 네이버 방문자 그래프 위젯 엔드포인트에서
자동으로 받고(위젯이 꺼져 있으면 빈 응답), 안 되면 `--visitors N`(어제 하루 값)으로 넣는다.
기록은 `content/naver/_metrics.csv`에 쌓인다.

**방문자 수는 검색 성과가 아니다.** 2026-09-28~10-04 주간 유입 39건 중 검색은 3건이었고 나머지는 홈판·블로그 내
이동이었다. 그래서 `manager.py`는 글마다 목표 키워드의 블로그 탭 순위도 조회해 `content/naver/_ranks.csv`에 쌓는다.
판정 기준 자체는 방문자 수 그대로다(바꾸려면 아래 규칙을 따른다). 대신 점검 시점에는 순위표와 사용자가 주는
유입분석 화면(검색 유입 건수)을 함께 보고, 방문자는 기준을 넘었는데 30위 안 글이 0편이면 스크립트가 경고한다.
같은 실행에서 원고의 `- GEO 질의:`마다 AI 브리핑을 조회해 우리 글이 인용됐는지도 `content/naver/_geo.csv`에 쌓는다.
인용은 방문과 별개라 판정에 넣지 않는다.

### 규칙 — 매니저도, 메인 세션도 따른다

- **판정을 순화해서 전달하지 않는다.** `전환권고`면 이 블로그가 기준에 미달했다고 말하고
  중단·컨셉 전환·기한부 연장 중에서 고르게 한다. 같은 컨셉 안의 미세조정을 대안으로 내놓지 않는다.
- **사용자가 반박해도 새 데이터가 없으면 판정은 그대로다.** 들인 노력·기대·의지는 근거가 아니다.
- **기준을 바꾸려면** `ADSENSE_PROGRESS.md`에 날짜·이전 값·새 값·사유를 적고
  `manager.py --selftest`를 같이 고친다. **`경고`·`전환권고`가 뜬 세션에서는 기준을 완화하지 않는다** —
  결과를 본 뒤에 고치는 기준은 기준이 아니다. 다음 세션에서 다시 논의한다.
- 수치가 없으면 추정으로 메우지 않는다.

### [검수 스크립트] 표기·구조를 바꾸면 검증 도구가 조용히 무력화된다 — 세 번째 재발 (2026-09-26)

**문제**: 네이버 원고의 플레이스홀더가 `[이미지: ...]` → `[이미지 ①: ...]`로 바뀌었는데
`check_naver.py`의 정규식이 콜론을 고정(`\[이미지:`)하고 있었다. 이미지·경험을 **0으로** 세고,
분량에서도 플레이스홀더를 못 걸러 1,505자를 1,728자로 보고했다. **에러는 안 나고 숫자만 틀렸다.**

**같은 패턴이 세 번째다.**

| 시점 | 무엇을 바꿨나 | 무엇이 조용히 깨졌나 |
|---|---|---|
| 2026-07-17 | blog-writer 메타 필드 5개 | `parse_blog_post()` 블록쿼트 화이트리스트 |
| 2026-08-22 | 썸네일 호스팅을 jsdelivr로 이전 | `verify_post.py` 카드 이미지 검증(`thumb/R800x0`) |
| 2026-09-26 | 원고 플레이스홀더 표기 | `check_naver.py` 이미지·경험·분량 카운트 |
| 2026-10-07 | (우리가 아니라 네이버가) 글 페이지 마크업 | `verify_naver.py` 본문 끝 표지 — 1,627자를 12,994자로 보고 |
| 2026-10-10 | 원고에 표를 쓰기 시작(12편~) | `verify_naver.py` 글자 크기 — 가장 많은 크기 하나만 봐서, 13편 스팬 148개 중 37개에 크기가 없는데 통과 |

네 번째는 우리가 바꾼 것이 아니라 **외부가 바뀐 경우**다. 셀프테스트는 우리가 표기를 바꿀 때만 깨지므로
이건 못 잡는다. 그래서 외부 HTML을 읽는 파서에는 "못 찾으면 예외"를 넣는다 — `verify_naver.parse()`는 본문
컴포넌트를 못 찾으면 `ValueError`, `keyword_research.serp()`는 결과가 10개 미만이면 `RuntimeError`다.
못 읽은 것을 0이나 기본값으로 돌려주면 그게 그대로 보고서에 실린다.

셋 다 **검증 대상의 표기·구조를 바꾸고 그걸 검증하던 스크립트를 같이 안 고쳤고**,
셋 다 **에러 없이 통과처럼 보였다.** 따로 찾아보지 않으면 영원히 못 알아챈다.

**해결 — 검수 스크립트에 `--selftest`를 고정한다.** 네이버 계열 셋은 전부 갖췄다.

```bash
python -X utf8 check_naver.py --selftest    # 원고 표기법 카운트
python -X utf8 verify_naver.py --selftest   # 라이브 HTML 파싱·카테고리·제목 지문
python -X utf8 naver_paste.py --selftest    # 마크다운 → 붙여넣기용 HTML (볼드 유지, 문장 단위 줄바꿈, 크기 15·나눔바른고딕)
python -X utf8 naver_prep.py --selftest     # 원고에서 이미지 경로를 넣는 순서대로 뽑기
```

`check_naver.py`는 2026-10-07부터 구조도 본다: 도입부에 목표 키워드와 숫자, 문장 60자, 문단 3문장,
볼드 30자·문단당 한 곳, 기준 연도. 규칙은 `NAVER_GUIDE.md` 「검색과 AI 요약에 걸리는 구조」「모바일 문장과 강조」.
발행된 01~09편은 판정에서 뺐다(`NEW_RULES_FROM`).
12편부터는 분량 1,500~2,500자, 표 3열 이하, 시각 요소(이미지+표) ≥ 소제목 수+1, `- 썸네일 문구:` 줄도 본다(`LENGTH_FROM`).
`verify_naver.py`는 발행 글의 글자 크기(기준 15 — 12편부터. 폰에서 16은 한두 글자 줄바꿈이 잦았다)·가운데 정렬 비율·표 개수를 보여준다.
카드 형태(큰 숫자·막대·타임라인·체크리스트)와 제목 썸네일은 `make_naver_images.py` — `--samples`, `--thumb NN`.

셀프테스트에는 **실제로 쓰는 표기법 그대로**를 합성 입력으로 넣고 카운트를 assert한다.
표기법을 바꾸면 셀프테스트가 먼저 깨진다.

**규칙**: 원고 표기·HTML 구조·API 필드에 의존하는 정규식을 손대면 **같은 커밋에서**
셀프테스트를 갱신하고 실행할 것. 티스토리 쪽은 `04_notion_upload.py --selftest`가 같은 역할이다.

### [verify_naver.py] 필드 하나만 보고 "없다"고 말하지 않는다 (2026-09-26)

1편 점검에서 `baLogData`의 `"tagNames":""`를 보고 "태그가 하나도 없습니다"라고 보고했다.
실제 태그 필드는 `var gsTagName = "..."`이었고 태그 10개가 정상적으로 들어가 있었다.
사용자가 멀쩡한 글을 수정하러 들어갈 뻔했다.

**규칙**: API·HTML에서 **필드 하나만 보고 "없다"고 단정하지 않는다.** 본문에서 실제 값을
교차 확인하고(예: 태그 문자열을 HTML 전체에서 grep), 확인이 안 되면 "이 필드에서는 안 보인다"로
범위를 좁혀 보고한다. 발행된 글을 고치라는 지시는 되돌릴 수 없는 작업이다.
